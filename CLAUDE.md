This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install                    # install dependencies
npm run dev                    # Next.js dev server (localhost:3000)
npm run typecheck              # tsc --noEmit
npm run build                  # next build (production build, no Cloudflare bundling)
npm test                       # vitest: pruebas de la lógica pura (src/**/*.test.ts)
npm run check                  # typecheck + tests + build, run this before considering a change done
npm run preview                # opennextjs-cloudflare build + wrangler dev (emulates the real Worker + D1 locally)
npm run deploy                 # opennextjs-cloudflare build + opennextjs-cloudflare deploy (publishes to Cloudflare)
npm run db:migrate:local       # apply migrations/*.sql to local D1 (.wrangler/state)
npm run db:migrate:remote      # apply migrations/*.sql to the production D1 database
npm run db:create-admin        # node scripts/create-admin.mjs "Full Name" username password [--remote]
npm run cf-typegen             # regenerate worker-configuration.d.ts from wrangler.json bindings
npm run demo:deploy            # sitio Demo (Google Play): D1 micongre-demo-db + Worker micongre-demo, migra, despliega y recarga datos ficticios; demo:seed solo recarga los datos
```

Tests (Vitest, `src/lib/__tests__/`) cover only the pure logic: eligibility core, auto-assign engine, NWScheduler CSV, JW Hub links, message templates, meeting dates, project hours and the per-group reports (`lib/reports/groups.ts`, shared by `/api/reports/groups` and its export). Keep business rules in pure functions so they can be tested, and add a test when you change one. There is no lint script and no UI/API coverage: run `npm run check` after any change and smoke-test through the browser (login → the module you touched).

Local dev needs a `.dev.vars` file (copy `.dev.vars.example`) with a `JWT_SECRET`. `next dev` picks it up via `initOpenNextCloudflareForDev()` in `next.config.mjs`, which lets `getCloudflareContext()` work outside of `wrangler dev` too.

Bootstrapping: while no user has `system_role='admin'`, `src/middleware.ts` redirects *every* route (pages → `/setup`, APIs → 409 `setup_required`) to the **setup wizard** (`src/components/setup/SetupWizard.tsx`); once an admin exists everything behaves normally and `/setup` redirects to `/`. The middleware caches "setup complete" per isolate, so after hand-wiping users in a dev DB restart the server. Wizard steps, each persisted immediately through public `/api/setup/*` routes (`src/lib/setup/service.ts`; all reject with 409 once an admin exists): welcome → source (Hourglass upload via a modal with progress + summary, or start empty) → congregation data (preloaded from the DB, i.e. from the migration), with an optional "Traer los datos desde JW.ORG" box (`JwCongregationLookup` → public `POST /api/setup/jw`, reusing `src/lib/jw/hub.ts`) that fills name, address and meeting times from a hub.jw.org link → super-admin account (name, username, password; created *last* and as a *hidden* admin so it doesn't count as a publisher; then the UI fades out and goes to `/panel`). A failed Hourglass import is rolled back, and it refuses to run over existing users. The mapping in `src/lib/setup/hourglass.ts` mirrors `scripts/import-hourglass.mjs` (keep them aligned). **NWScheduler** source (`src/lib/setup/nws.ts`, `NwsImportModal`, `POST /api/setup/nws`): NWS exports one CSV per option, so the modal asks for up to five (Personas required; Contactos de emergencia, Informes, Discursantes, Programa de discursos públicos optional). Files are recognised by their header columns, never by file name; the same pure `buildNwsImport` runs in the browser for a dry-run preview and on the server for the real (all-or-nothing, rolled back with `wipeAllData`) import. Reports/speakers/program rows are joined to people by normalised name (repeated names are skipped with a warning). Referenced talk outlines missing from the catalog are created as `Discurso N` placeholders. Third source: **restore a MiCongre backup** (`POST /api/setup/restore`). Backups (`src/lib/backup/backup.ts`) are generic JSON dumps of every table (discovered from `sqlite_master`; catalogs `privileges`/`appointment_privilege_rules` and session/activation tokens excluded); restore validates table/column names against the live schema and runs in one D1 batch with `defer_foreign_keys`. Admin-only **Congregación → Zona de peligro → Borrar todos los datos** (`DeleteAllDataCard`) downloads that backup via `GET /api/congregation/backup`, then `POST /api/congregation/reset` wipes everything except catalogs, which puts the app back in setup mode (the middleware caches "setup complete" for only 30 s for this reason). `db:create-admin` is still the CLI alternative.

## Architecture

Congregation-management web app (Jehovah's Witnesses congregation administration — publishers, appointments/privileges, meeting scheduling, operational tasks, service reports, attendance). Next.js 16 App Router (keep `middleware.ts`: the new `proxy` file runs on the Node runtime, which OpenNext/Workers do not support yet; Next prints a deprecation warning), deployed to Cloudflare Workers via OpenNext, with Cloudflare D1 (SQLite) via Drizzle ORM. Phase 1 of 2 — a future Android app (not in this repo) will consume the same `/api/auth/*` and other API routes, which is why auth is token-based rather than pure server-session.

### Migrations are hand-written, not drizzle-kit-generated

`migrations/*.sql` is applied via `wrangler d1 migrations apply` (the numbering convention from the original Cloudflare D1 template). `drizzle.config.ts` exists only to power `drizzle-kit studio`; **do not run `drizzle-kit generate`** — it would produce a second, disconnected migration history. When the schema in `src/db/schema/*.ts` changes, hand-write the matching SQL in a new `migrations/NNNN_*.sql` file with the same column names/types/constraints, and apply it locally and (when ready) remotely. `migrations/0009_field_service_groups.sql` is the pattern to follow when a column's FK target doesn't exist yet at table-creation time (add the column later via `ALTER TABLE`).

### Auth: dual web/mobile from day one

`src/lib/auth/*` implements auth from scratch (no Auth.js) with only Web Crypto (`crypto.subtle`), so it runs identically in Workers and in `next dev`:
- Passwords: PBKDF2-SHA256 (`password.ts`), never bcrypt/argon2 (those need node-native bindings Workers doesn't have).
- Access tokens: hand-rolled HS256 JWT (`jwt.ts`), 15 min TTL, carries `privs` (privilege codes) so most requests don't need a DB round-trip to check authorization.
- Refresh tokens: opaque, hashed at rest (`refresh_tokens` table), rotated on every use; **reusing an already-rotated token revokes the entire session family** (`api/auth/refresh/route.ts`) — this is the theft-detection path. Sessions never expire (10-year sliding TTL). If a client comes back with the previous token because it never received or saved the new one (network drop, app killed or updating mid-refresh), the server recognises it because the successor was **never used** and rotates from it instead of revoking everything (`rotateRefreshToken` in `lib/auth/refresh.ts`); reusing a token whose successor was already used is still treated as theft. A request that lost a concurrent-rotation race within `ROTATION_RACE_GRACE_MS` (2 min) gets an access token instead; the Android app also refreshes one-at-a-time per account (`RefreshLocks`) and only marks an account «Sesión vencida» on a 401 from refresh, never on 5xx/network errors.
- Every `/api/auth/*` route sets httpOnly cookies **and** returns the tokens in the JSON body in the same response — the web client uses the cookies, a future mobile client uses the JSON. `src/middleware.ts` and `src/lib/auth/session.ts` both resolve identity the same way: cookie first, `Authorization: Bearer` header as fallback.
- There is no email/password-reset-by-email flow. Login is by `username` (system-generated, see below), because email addresses are unreliable for this user base. The only account-provisioning path is the **activation link**: an admin generates a one-time link from a publisher's detail page (`AccessPanel.tsx` → `POST /api/publishers/[id]/access`), the recipient opens it (`/activar/[token]`), and `POST /api/auth/activate` generates a username + password for them and logs them in immediately — nobody ever invents their own password. See `docs/mobile-activation-protocol.md` for the exact contract the future Android app must implement against the same endpoint (it's designed to work as an Android App Link against the identical URL).
- **Web multicuentas** (varias personas en un mismo navegador, sin contraseña al cambiar): la cuenta activa sigue siendo `mc_access` + `mc_refresh` (por eso `getSession()` y el middleware no cambian); las demás se guardan en la cookie httpOnly `mc_accounts` (`[{id, name, refresh}]`, máx. 5; `lib/auth/accounts.ts`). Solo el refresh de la cuenta activa se rota: `POST /api/auth/switch` rota el de la que entra y guarda el de la que sale; `login` y `activate` guardan la cuenta que estaba activa (`rememberPreviousAccount`) y cerrar sesión solo cierra la activa; `POST /api/auth/accounts/remove` ("Quitar de este dispositivo") revoca el refresh guardado; `GET /api/auth/accounts` devuelve solo nombres. UI: `components/auth/useAccounts.ts`, selector en `ProfileMenu` (escritorio) y `MoreMenu` (móvil), "Agregar cuenta" = `/login?add=1` y "Continuar como…" en el login. No afecta a la app Android (usa su propio `AccountStore`).
- **¿Olvidaste tu contraseña?** (login web, `components/auth/ForgotPassword.tsx` → público `POST /api/auth/forgot`, `lib/auth/passwordHelp.ts`): busca por usuario o nombre completo (único) y avisa (notificación + push) a admins, a quien tiene `accounts_admin` y al superintendente/auxiliar del grupo, que generan un «Nuevo enlace» en la ficha. Responde siempre igual; límite 1 aviso por persona cada 6 h y 5 solicitudes por IP por hora (tabla `password_help_requests`, `migrations/0066`; la IP real llega del router en `x-client-ip`).
- **Eliminar cuenta** (requisito de Google Play): `POST /api/auth/delete-account` (`{password}`, desde Mi perfil web o la app) llama a `lib/auth/deleteAccount.ts::removeAccountAccess`: borra usuario, contraseña, sesiones, tokens de dispositivo, suscripciones push y enlaces de activación y deja `account_status='no_account'`, **pero no borra al publicador** (ficha, nombramientos, informes: son registros de la congregación; quien los quiera borrar se lo pide a un admin). Un admin que sea el último con acceso recibe 409 `last_admin`. Las URL públicas que pide Play (privacidad, eliminar cuenta) y el `assetlinks.json` del dominio comodín los sirve `micongre-router`; este repo también sirve `/.well-known/assetlinks.json` (`lib/android/assetlinks.ts`, mantenerlo igual que el del router) para los sitios en `workers.dev`. **Sitio Demo** (cuenta de prueba para Google Play, `https://demo.micongre.app`): ver `docs/demo.md`.

### RBAC: one eligibility engine, reused everywhere

`src/lib/rbac/eligibility.ts::getEligiblePublishers(db, privilegeId)` is the single source of truth for "who is allowed to do X". It unions two paths — automatic eligibility via an active `theocratic_appointments` row matched against `appointment_privilege_rules`, and direct grants in `user_privileges` — then filters by the privilege's hard constraints (`requires_male`, `requires_baptized`, `requires_adult`/parental-consent). Every "assign a person" UI (meeting planners, operational matrix, weekend roles) calls the **same function** to populate its dropdown and the API re-calls it via `assertEligibleForAssignment()` before persisting, so a stale or tampered client can never force an invalid assignment. `PRIVILEGE_IDS` in `src/lib/rbac/roles.ts` hardcodes the literal `id` values seeded in `migrations/0005_privileges_rbac.sql` — server and client code reference privileges by these constants rather than looking up `code → id` at runtime.

En pantalla (ficha de la persona y asignación masiva) los privilegios se agrupan y ordenan por código con `lib/rbac/privilegeGroups.ts` («Administrar», «Superintendente de circuito», «Administrar por grupo», «Notificaciones», «Predicación», «Reuniones», «Fin de semana», «Vida y Ministerio Cristiano», «Operativo»; uno nuevo sin grupo cae en «Otros»): es solo presentación, `privileges.category` no cambia (el módulo de acomodadores filtra por `operational`). Al agregar un privilegio, ponlo en su grupo (la prueba exige que estén todos los de `PRIVILEGE_CODES`). Los nombres se acortaron en `migrations/0077` porque el grupo ya da el contexto.

`GET /api/privileges/eligible?privilegeIds=a,b,c` batches multiple privilege lookups into one request — meeting-planner and operational-matrix pages fetch the full set of privilege IDs they might need once on load, rather than one request per dropdown.

Other guards in `src/lib/rbac/guards.ts`:
- `assertCanManageReport(db, session, targetUserId)` — the dual-authorship rule for S-4 reports: a publisher manages their own, **or** the superintendent/assistant of their `field_service_group` (verified by both the group's `overseerUserId`/`assistantUserId` *and* an active `field_service_group_overseer`/`assistant` appointment), **or** any admin (admins bypass the group check entirely).
- `assertCanRecordAttendance(session)` — admin or the `meeting_attendance_recorder` privilege; this is why `/api/midweek` and `/api/weekend` GET (list only, not the `[id]` detail) are open to any authenticated user rather than admin-only — a non-admin attendance recorder needs to see meeting dates to pick which one to record.
- `isValidAssistantPairing()` in `eligibility.ts` — same-sex-or-same-`householdId` rule for a student assignment's assistant.

### Validación (zod 4)

Los esquemas de edición (PATCH) se arman con `patchSchema(createXSchema)` (`lib/validation/patch.ts`), **nunca** con `.partial()`: en zod 4 `.partial()` rellena los `.default()` y un PATCH que no manda un campo lo regresaría a su valor por omisión. Los id se validan con `z.guid()` (formato UUID sin exigir la versión RFC) y el correo con `z.email({ pattern: z.regexes.html5Email })`. Prueba: `__tests__/zod4.test.ts`.

### Schema quirks worth knowing before touching them

- `operational_schedules` and `meeting_attendance` are **polymorphic**: `meetingType` (`midweek`|`weekend`) + `meetingId`, no real FK, because SQLite/D1 can't FK to one of two tables. Integrity is enforced in application code (`src/lib/collision.ts` resolves the right table per `meetingType`).
- `midweek_assignments` has generic `mainAssigneeId`/`assistantAssigneeId` columns reused across very different section types. The "Estudio bíblico de la congregación" section is modeled as **two separate rows** (conductor + reader, each with its own `privilegeId`, distinguished by `sectionTitle`) rather than adding more columns — see `MIDWEEK_FIXED_SECTIONS` in `roles.ts`. `student_assignment` is the only section type that isn't auto-seeded when a meeting is created (its count varies week to week); everything else is seeded once via `MIDWEEK_FIXED_SECTIONS`.
- `service_reports.userId` (whose report it is) is deliberately separate from `enteredByUserId` (who actually typed it in) — needed for the dual-authorship feature above without a full audit-log table.
- `users.account_status` (`no_account`/`invited`/`active`/`disabled`) is independent of `congregationStatus` (active/inactive/irregular) and of having appointments/privileges — a student or a child can exist fully in the system with no login ever provisioned.
- Collision detection (`src/lib/collision.ts`) is advisory only (returned as `warnings[]` on the assignment response), never blocking — an admin can still save an assignment that double-books someone.

### Limpieza del Salón del Reino (`/cleaning`)

Módulo gateado por el privilegio `cleaning_admin` ("Administrar → Limpieza", otorgado a mano; admin siempre puede), con la terminología de la Guía y el Cronograma oficiales (`src/lib/cleaning/labels.ts`, incluye un resumen de las guías). Tres tipos (`cleaning_tasks.kind`): **ligera** (después de cada reunión; una tarea por reunión, `meeting_type` + `meeting_id` polimórfico sin FK real, igual que `operational_schedules`), **profunda** (cada semana; `week_start` = lunes) y **a fondo** (por lo menos una vez al año; `task_date`, se programa a mano y puede haber varias). Los responsables (`cleaning_task_assignees`, varios por tarea) son un **grupo de servicio nuestro**, **toda nuestra congregación**, u **otra congregación del salón** (catálogo `cleaning_congregations`, pestaña "Congregaciones del salón"): lo que queda a cargo solo de otra congregación no genera avisos en la nuestra. Las tareas ligera/profunda se crean al asignar o marcar por primera vez y se borran solas al quedar sin responsables ni marca (`lib/cleaning/tasks.ts`); valida el responsable **antes** de crear la tarea.

Asignar (`POST /api/cleaning/assignees`) no avisa: el botón **Enviar notificación** de cada fila (`POST /api/cleaning/tasks/[id]/notify`) crea una `notifications` por responsable nuestro (scope `group` con el `groupId` asignado, o `congregation` si es toda la congregación; `expiresAt` = fin de la limpieza; cada integrante puede ocultarla) más el push, y reenviar o quitar al responsable borra el aviso anterior. El recuadro "Realizada" (`POST /api/cleaning/complete`) es el que marca el coordinador de limpieza en el cronograma. La asignación aparece en "próximas asignaciones"/"historial" de Mi Panel (`getUserAssignments`, con `dateEnd` para la semana de la profunda) con o sin aviso; reuniones canceladas o borradas se omiten. **Generar cronograma** (`/cleaning/schedule`, `lib/cleaning/schedule.ts`) dibuja el formulario oficial del año (ligera ES/FS por semana 1–5 × mes, profunda, a fondo), con o sin lo asignado, para imprimir/guardar como PDF; cada semana cae en el mes de su lunes. D1 limita a 100 parámetros por consulta: los `inArray` que pueden crecer usan `chunked()`.

### Territorios (`/territories`)

Acceso: admin o el privilegio `territory_management` («Administrar → Territorios»), que reciben solos el superintendente de servicio y el siervo de territorios (reglas en `migrations/0046`). Dos tipos (`territories.kind`): **general** y **public_preaching**; los dos admiten polígonos, líneas, puntos y textos (`ALLOWED_TOOLS`; `hasDisallowedFeatures` queda por si se vuelve a restringir). El dibujo es un GeoJSON FeatureCollection en `territories.map_data` (los textos son `Point` con `properties.kind="text"` y `size` normal/medium/large; los puntos pueden llevar `emoji`, `label` —etiqueta pegada debajo a cualquier zoom— y `departure` —punto de salida a la predicación, un pulso verde; puede haber **varios**, cada uno con nombre (`label`) y dirección escrita (`address`), los dos obligatorios al guardar, y uno `departureDefault`; `listDepartures`/`resolveDeparture` en `geo.ts`). «Ver todo» muestra solo los polígonos de cada territorio con su número, y se exporta como PNG con la simbología (color, número y nombre) a la izquierda (`TerritoryMapController.exportPng`). Mapa base gratuito: teselas vectoriales de OpenFreeMap con MapLibre GL, estilo "bright" sin nombres de lugares (`lib/territories/mapStyle.ts`); `lib/territories/mapController.ts` es el editor (solo cliente; puntos y textos son marcadores HTML para que se vean los emojis) y `importFile.ts` importa KML/KMZ/GeoJSON. Se puede encargar un territorio solo a quien tenga el privilegio otorgado a mano "Asignable para territorio" (tipo General) o "Asignable para predicación pública" (`migrations/0047`; `listAssignableUsers`, que `assignTerritory` revalida). El módulo tiene tres pestañas: **Asignaciones** (listado con acciones de administrador: avisar, completar, devolver, cancelar, eliminar), **Territorios** (una tarjeta por territorio) y **Registro** (S-13 por año de servicio, septiembre a agosto, solo web: `lib/territories/s13.ts` puro con pruebas. Cada asignación del territorio que estuvo vigente en el año es una línea y cada salida de predicación ya hecha a ese territorio (`preaching_session_territories.assignment_id`, o por fechas si es vieja) es una casilla «Asignado a»: nombre del capitán, fecha en que se predicó y, solo si ese día se completó, esa fecha en «se completó»; 4 casillas como el formulario, más si hace falta (hasta 8, luego sigue abajo). «Última fecha en que se completó»: al completarse una asignación, esa fecha va también en su línea; la primera línea de un territorio que no se completó lleva la última completada antes del año. Datos en `record.ts` / `GET /api/territories/record`; se descarga (solo los territorios con asignaciones en el año) con el formato oficial en tamaño **Carta** (vertical hasta 5 casillas, horizontal con más; `s13Svg.ts`, export `s13`) como imagen —una por hoja— o **PDF** de varias páginas (`ExportFormat` `pdf`, `imagesToPdf` en `lib/export/pdf.ts`, siempre Carta, sin dependencias)). Cada asignación (`territory_assignments`) queda de historial; a lo más una vigente por territorio. Asignar no avisa: el botón **Enviar** (`POST /api/territories/[id]/notify`) crea la notificación + push. En Mi Panel el territorio sale como asignación hasta que el encargado lo **completa** o **devuelve** (comentario opcional, con confirmación; `POST /api/territories/assignments/[id]/resolve`, solo el propio encargado), y eso avisa (notificación + push) a quienes tienen el privilegio. Los `title` de `Button` y `components/ui/Tooltip` son el globito de ayuda estándar de la app.

### Calendario (`/calendar`)

Módulo para **toda la congregación** (arriba del menú, después de Mi panel, junto a Reuniones y Avisos: `TOP_ITEMS` en `navItems.ts`; en la barra inferior del celular están Panel, Reuniones, el acceso directo, Avisos y «Menú» —antes «Más»—; en Android, «Más» → Calendario y, como antes con la predicación, tocar Mi Panel estando en Mi Panel abre el Calendario y tocarlo otra vez vuelve; la web móvil hace lo mismo con la pestaña Panel). `GET /api/calendar?month=AAAA-MM` devuelve `preaching` (lo mismo que el calendario de predicación: quien administra el módulo ve todas las salidas, los demás las que les tocan; con `canChangeDeparture` y `mapKinds`) e `items`: todo lo demás con fecha, armado por `lib/calendar/build.ts::buildCalendarItems` (puro, con pruebas) desde `lib/calendar/service.ts`: eventos de la congregación (varios días: `dateEnd`), reuniones de entre semana y fin de semana (fecha y hora reales; las canceladas no salen) y las asignaciones de la persona de `getUserAssignments` (partes y acomodadores → `assignment`, limpieza, discursos fuera → `talk`, pastoreos; los territorios y solicitudes no). Un color por tipo, igual en web (`components/calendar/CalendarModule.tsx`, `KIND_COLOR`) y app (`CalendarScreen.kt`); hoy resaltado. Quien administra la predicación agrega salidas tocando un día (app). El widget de predicación de Android muestra las mismas salidas que el calendario de la app: sigue su filtro «Solo las mías / Todas» (`GET /api/preaching/calendar?all=0|1`; sin `all`, quien administra ve todas). El menú «Predicación» de la app se reemplazó por «Calendario».

### Precursorado (`/pioneer`)

Herramientas **personales** del precursor (`lib/pioneer/`, reglas puras en `rules.ts` con pruebas). Acceso: el privilegio `pioneer_tools` («Herramientas de precursor», `migrations/0081`), que dan solos los nombramientos `regular_pioneer`, `auxiliary_pioneer` y `special_pioneer`; **ser admin no basta** (`canUsePioneerTools`, y en el menú `privilegeOnly`), porque cada quien ve y cambia solo lo suyo (todas las consultas filtran por `userId`). Tres pestañas:
- **Progreso** (`GET /api/pioneer/progress?serviceYear=`, `progressMonths` en `rules.ts`): barras de los 12 meses del año de servicio elegido (septiembre a agosto; por mes cuenta el informe enviado —servicio + proyectos— y, si aún no hay, lo anotado, que se dibuja tenue) y abajo el velocímetro (`HoursGauge` de `RegularPioneerCard`) con el total contra 600.
- **Horas** (`pioneer_hours`): registro manual (fecha, horas con decimales, comentario), por mes, con el total.
- **Estudios** (`pioneer_studies`): nombre, estado (`return_visit` Revisita, `active` Activo, `progressive` Progresivo, `finished` Terminado), día de la semana de la visita (`weekday` 1 = lunes … 7 = domingo), comentario y punto opcional en el mapa (`components/pioneer/PointPicker.tsx`: pin fijo en el centro, se mueve el mapa; abre en el Salón si la congregación tiene coordenadas). Un ícono de mapa («Ver todos los estudios», `StudiesMap.tsx`) muestra en un solo mapa los del filtro elegido que tienen ubicación (pin por estado con el nombre). El job diario (paso `studies`) avisa por push el día **anterior** al día anotado (no terminados).
- **Informe:** `GET /api/reports/s4/mine` devuelve `prefill` (solo si aún no hay informe del mes y la persona tiene el privilegio): la suma de las horas con fecha en ese mes y cuántos estudios están Activo o Progresivo; `S4Form` (web) y la app lo precargan.

### Literatura (`/literature`)

Acceso: admin o el privilegio `literature_access` («Administrar → Literatura»), que recibe solo el nombramiento `literature_servant` (siervo de literatura) y a los auxiliares se otorga a mano (`migrations/0079`). Cinco pestañas (`components/literature/`, servicio `lib/literature/service.ts`, reglas puras `rules.ts` con pruebas):
- **Solicitudes** (`literature_offers` + `literature_offer_responses`): se ofrece una publicación a los **publicadores** (con cuenta activa, cada uno responde por sí) o a los **superintendentes de grupo** (responden por su grupo), con mensaje opcional y **fecha de fin**. Crear no avisa: **Enviar** (`POST /api/literature/offers/[id]/send`) la pone en Mi Panel y manda el push (reenviar avisa solo a quienes no han respondido). En Mi Panel (`components/panel/LiteratureOffers.tsx`, `GET /api/literature/offers/mine`, `POST …/respond`) cada uno dice **Sí** (con cantidad) o **No** y puede cambiarlo hasta la fecha de fin; después la tarjeta desaparece sola. La **X** («Quitar de Mi Panel», `POST …/dismiss`, tabla `literature_offer_dismissals`, `migrations/0082`) la quita antes, haya respondido o no: lo respondido se conserva y reenviar ya no le avisa. El módulo muestra la lista (sí con cantidad y total, no, sin responder) y la descarga (`literature-offer`). No hay flujo de entrega: solo la lista. Ya enviada, no se cambia la publicación ni a quién va.
- **Pedidos** (`literature_orders`, `migrations/0084`, `OrdersTab`, `GET/POST /api/literature/orders`, `PATCH/DELETE …/[id]`): lo que un publicador pidió por su cuenta (publicación, cantidad, nota y quién). Solo registro del siervo de literatura: no avisa a nadie. Cada pedido se puede **archivar** (`archived_at`): sale de la lista y se ve con el filtro «Archivados» (`?archived=1`).
- **Inventario** por cortes (`literature_inventories` + `literature_inventory_items`): cada corte es un conteo en una fecha con publicación + ubicación + cantidad (una línea por par; repetirla reemplaza la cantidad). Un corte nuevo puede empezar con lo del anterior. Descarga `literature-inventory`.
- **Catálogo** (`literature_publications`): precargado de la Biblioteca de JW.ORG en español (`migrations/0080`, Biblias, libros, folletos, tratados y revistas desde 2014; id fijo `pub_<código>[_<número>]`, `issue` = AAAA-MM en revistas). `lib/literature/jwCatalog.ts` lee las páginas de la Biblioteca (`data-pub`, `data-issue`, título, portada) y agrega lo nuevo revisando la primera página de cada sección y las revistas del año en curso y el siguiente: lo corren el job diario (paso `literature`) y el botón «Actualizar desde JW.ORG». Se pueden agregar publicaciones a mano (y borrarlas si no se usan) y **cambiar** cualquiera (`PATCH /api/literature/publications/[id]`: nombre y tipo; el código solo de las agregadas a mano). La actualización desde JW.ORG solo agrega (`onConflictDoNothing`), así que no pisa esos cambios. «Borrar todos los datos» conserva el catálogo.
- **Ubicaciones** (`literature_locations`): catálogo que solo se elige en el inventario; una ya usada en un corte no se borra.

### Jobs programados (crons)

Dos crons de Cloudflare (`wrangler.json` → `triggers.crons`), despachados por `event.cron` en `custom-worker.js` hacia rutas internas `/api/cron/*` (secreto `x-cron-secret` = HMAC de `JWT_SECRET`, `lib/reminders/secret.ts`; sin él, 404):
- **Job de asignaciones** (`0 * * * *`, `/api/cron/reminders`, `lib/reminders/run.ts`): cada hora, pero solo actúa lunes y viernes (hora de Nicaragua, UTC−6) desde `reminderHour` de Congregación, una vez al día; avisa (feed de Mi Panel + push) las asignaciones de la semana o del fin de semana. `?force=1` lo fuerza.
- **Job diario** (`0 11 * * *` = 5:00 a. m. Nicaragua, `/api/cron/daily`, `lib/jobs/daily.ts`): arma los programas del mes en curso y el siguiente (entre semana desde la guía mwb, o con las partes fijas si aún no se publica y se completa después mientras nadie esté asignado; fin de semana: el sábado que falte; lo existente no se toca), ajusta los puestos de tareas operativas de las reuniones desde la semana en curso a la plantilla (ver «Puestos de tareas operativas») y actualiza desde el JW Hub las `speaker_congregations` con `jw_url`. (3) Recuerda por push (mensaje amistoso, sin entrada en el feed) el informe de servicio del **mes anterior** a quien aún no lo envió, cada día (`lib/reminders/reports.ts`: personas activas con cuenta, estado activo en la congregación y no estudiantes; un informe del mes que no esté `not_submitted` cuenta como enviado). (4) Agrega al catálogo de literatura las publicaciones nuevas de JW.ORG (paso `literature`). (5) Avisa por push a cada precursor los estudios que tiene **mañana** según el día anotado (paso `studies`, ver «Precursorado»). (6) Aplica el catálogo central de bosquejos del router (paso `outlines`, ver «Bosquejos (S-99a)»). `?only=programs|congregations|reports|preaching|events|literature|studies|outlines` corre un solo paso. Las filas del programa mwb las genera `lib/mwb/programRows.ts` (compartido con `api/midweek/import`).

### Solicitud de actualización de datos (Mi Panel)

Una fila por persona y tipo en `data_update_requests`; solo a quien tiene cuenta activa y sin repetir lo pendiente; avisa por push. Quien la recibe ve primero en Mi Panel (web y app) una tarjeta por cada cosa pedida («Solicitan que actualices tus datos…» / «…tu contacto de emergencia…») y al tocarla un modal precargado solo con esos datos (`GET/POST /api/data-requests/mine`); al guardar se cierran esas solicitudes.

«Mi grupo de servicio» de Mi Panel: el nombre del grupo en grande (contraído por omisión: al tocarlo se despliega) y la lista para contactar con el superintendente, el auxiliar y los demás por nombre (`group.people` en `/api/panel/summary`, con `role`; `members` sigue sin ellos para las versiones anteriores de la app).

### Botones de grupos de Mi Panel

`/api/panel/summary` arma los botones (`links`) según los nombramientos vigentes de quien consulta; cada grupo de WhatsApp tiene URL + color en Congregación → Enlaces de Mi Panel (`congregations.link_*`): **congregación** (todos), **nombrados** (siervos ministeriales y ancianos), **ancianos**, **precursores regulares** (`regular_pioneer`), **siervos ministeriales** (solo `ministerial_servant`, no ancianos) y **comité** (`SERVICE_COMMITTEE_APPOINTMENTS`: coordinador, secretario y superintendente de servicio, `migrations/0067`). ### Puestos de tareas operativas (plantilla)

Pestaña **Plantilla** del módulo **Acomodadores** (antes «Tareas operativas»; privilegio de acceso «Administrar → Acomodadores», `migrations/0069`; el código sigue llamándolo `operational`) (`components/operational/OperationalTemplate.tsx`, `GET/PUT /api/operational/template`, `lib/operational/template.ts`): cada congregación define qué puestos lleva cada reunión de entre semana y de fin de semana (tabla `operational_template_slots`, `migrations/0068`); una tarea puede repetirse y `position` (opcional) le da un nombre, que también puede repetirse (p. ej. dos «Entrada»: `migrations/0087` quitó el índice único de `operational_schedules`; cada asignación se edita por su id). Mientras `congregations.operational_template_set` sea 0 vale la plantilla por omisión (un puesto por cada privilegio operativo de reunión), por eso no se siembran filas y un borrado de datos vuelve a ella. `planSlotSync` (puro, con pruebas) ajusta una reunión: agrega lo que falte y quita lo que sobre o no esté en la plantilla **solo si nadie lo ocupa**. Se aplica al abrir una reunión sin puestos (`GET /api/operational`), al guardar la plantilla (reuniones desde el lunes de la semana en curso) y en el job diario. Un puesto agregado a mano en una reunión y sin asignar desaparece en la siguiente corrida. El planificador y el reporte siguen el orden de la plantilla (`sortByTemplate`: la n-ésima repetición de una tarea ocupa el lugar de la n-ésima en la plantilla), muestran una fila por asignación y, si tiene nombre, ese nombre en lugar del de la tarea (`slotDisplayName`). En la interfaz se habla de «asignaciones», no de «puestos».

Regla de semanas y meses: una semana (lunes a domingo) pertenece al mes de su **lunes**. Así lo hacen la importación de la guía mwb y de La Atalaya, el job diario, el cronograma de limpieza y los reportes «Todo el mes» (`parseRange` en `lib/export/builders/meetingDates.ts`: del primer lunes del mes al domingo de la semana del último lunes; prueba `meetingRange.test.ts`). Los reportes de acomodadores, entre semana y fin de semana tienen además **«Rango de fechas»** (variante `range: true` de `ExportButton`: «Desde»/«Hasta», `scope=range&from&to`, máx. 186 días; acomodadores filtra por la fecha real de cada reunión y los programas toman las semanas completas que toca el rango, `weekSpan`). Lo que es por reunión y no por semana (promedios de asistencia) cuenta en el mes en que se celebra la reunión.

Norma de UI: el botón de reporte va arriba del todo, en las acciones del encabezado (`PageHeader actions`, junto al título); si ya hay otro reporte ahí, se pregunta dónde agregar el nuevo. Todos los reportes con tema (no los formatos oficiales) llevan el nombre de la congregación como primera parte del subtítulo (`api/export/[kind]`).

### Punto de salida de cada predicación

Cada territorio de una salida de predicación guarda el punto de salida elegido (`preaching_session_territories.departure_fid`, `migrations/0078`; null = el predeterminado del mapa). Lo elige quien programa la salida (formulario de Predicación, web y app, si el territorio tiene más de uno) y lo cambian, desde el Calendario (web y app) y el widget, quien administra la predicación o los territorios, el **secretario** y el **siervo de territorios** (cualquier territorio: `canManageDepartures` en `guards.ts`) y el **capitán** (quien tiene el territorio asignado) solo el de su territorio (también desde Mi Panel), **antes de la salida o hasta 2 horas después** (`lib/preaching/departureRules.ts`, con pruebas; `POST /api/preaching/[id]/departure` → 409 `departure_locked` fuera de plazo). Si ya se avisó, el cambio reenvía el aviso con «Cambió el punto de salida». El punto del día (nombre — dirección) va en el aviso y el push, el calendario (`departure`, `departures` y `canChangeDeparture` por territorio en `/api/preaching/calendar`), Mi Panel (`detail` y `departureChoices`) y el widget; las recurrentes copian el punto. El texto del territorio («Lugar de reunión», `meeting_place`) se muestra como **Indicaciones** y acompaña al punto.

**Mensaje de WhatsApp de la predicación:** en el encabezado de Predicación (web) y en el Calendario de la app (solo quien administra la predicación, `canAccessPreachingModule`) hay dos botones, «Entre semana» (lunes a viernes) y «Fin de semana» (sábado y domingo). `GET /api/preaching/whatsapp?kind=weekday|weekend&week=current|next` arma el texto (`lib/preaching/whatsapp.ts`, puro con pruebas): título con el rango de los días que tienen predicación («Predicación del 17 al 20 de noviembre»), y por día la hora, el territorio y el punto de salida elegido. «Esta semana» va desde hoy (el de entre semana pasa a la próxima si hoy es sábado o domingo). Se abre en WhatsApp con el texto escrito (web: `wa.me/?text=`; app: `ACTION_SEND` a WhatsApp o WhatsApp Business, luego wa.me y, solo si no hay nada, se copia): WhatsApp no deja elegir el grupo desde un enlace, se elige allí.

### Predicación recurrente

Una salida de predicación (`preaching_sessions`) puede marcarse **Recurrente** (`recurring`, `migrations/0070`): se repite cada semana el mismo día y hora, con los mismos territorios y destinatarios, mientras cada territorio siga con la misma asignación (el mismo capitán) que tenía al programarla (`preaching_session_territories.assignment_id`). `lib/preaching/recurring.ts::runRecurringPreaching`: el job diario (`?only=preaching`), el día de la salida, crea la de la semana siguiente con sus avisos y le **pasa la marca** (solo la más reciente de la serie la lleva); al completar, devolver o borrar una asignación de territorio (`lib/territories/service.ts`) se quitan esos territorios de la salida pendiente (sin territorios se borra) y la serie termina. Las salidas pasadas no se tocan. Cada territorio tiene un **Lugar de reunión** opcional (`territories.meeting_place`, multilínea, hasta 500 caracteres, `migrations/0071`) que la tarjeta del día del calendario (web y Android) muestra debajo de los destinatarios, sin etiqueta; la tarjeta muestra el nombre del territorio (o «Territorio N» si no tiene). Botón de **mapa** en esa tarjeta: `territoryMapKinds(session)` (`guards.ts`) dice de qué tipos puede abrir el mapa (quien administra territorios: todos; «Asignable para territorio» → general; «Asignable para predicación pública» → predicación pública); `/api/preaching` y `/api/preaching/calendar` lo devuelven como `mapKinds` y `GET /api/territories/[id]/map` aplica la misma regla.

### Mi Panel → «Mis asignaciones» (próximas)

`/api/panel/summary` toma solo lo de la **semana en curso, hasta el domingo** (el lunes empieza la siguiente; no «los próximos 7 días»), más los territorios pendientes que ya toca mostrar —solo desde el **día antes de su siguiente salida de predicación** de esa asignación y hasta **2 horas después** de ella (luego se oculta hasta el día antes de la siguiente); sin salida programada no sale (`nextTerritorySession`, `territoryVisible`, `sessions`)—, y lo pasa por `lib/panel/upcoming.ts::selectUpcoming` (puro, con pruebas) para mostrar solo lo que sigue: de las reuniones, todo lo de la siguiente de entre semana y de la siguiente de fin de semana (partes y acomodadores, `bucket` `meeting:midweek|weekend`); los discursos que da la persona en otra congregación, todos los de la semana en curso (o el siguiente); los territorios pendientes que se muestran, todos, y una salida de predicación cuyos territorios son todos del capitán no se repite (el territorio se presenta como ella). La predicación se escribe «Predicación: 8:45 a. m. Territorio» (también el territorio del capitán) y al tocarla abre el Calendario en ese día (`openDate`; web `/calendar?date=`, app `Dest.Calendar(date)`); sale 2 horas después de su hora (`until`); de lo demás (limpieza, predicación con la congregación o el grupo, predicación pública, pastoreo) solo el siguiente. Las asignaciones de reunión (partes, acomodadores, limpieza ligera) usan la fecha real (`effectiveMeetingDate`, día de reunión de Congregación), así pasan al historial solo después del día de la reunión. Quien administra los arreglos de discursos (admin, `weekend_access` o nombramiento `public_talk_coordinator`) ve además «Sale … a …» por cada discurso saliente de la semana en curso. Los campos auxiliares de `PanelAssignment` (`bucket`, `time`, `territoryIds`, `when`, `nextSession`) no se envían al cliente. **Mi historial** (solo web): lo de los últimos 7 días, en gris, solo los 3 más recientes. Es solo del servidor: la app Android lo recibe igual, sin actualizarse.

### Route/module dependency order

If extending the app, this is the order things were actually built in and the order their data dependencies require: schema/migrations → auth → RBAC eligibility engine → publishers (+ appointments/privileges grants, which live under `api/publishers/[id]/...`) → field service groups → the two meeting planners (midweek, weekend — independent of each other, both depend on eligibility) → operational tasks matrix (depends on both meeting planners existing, for collision checks) → reports/attendance (depends on field service groups for dual authorship) → the regular-user panel (`/panel`, reads across all of the above via `src/lib/queries/panel.ts`, built last since it has no writes of its own besides self-service S-4).

Admin-gated pages redirect to `/panel` server-side (`if (session?.role !== "admin") redirect("/panel")`); a few pages (`/reports`, `/reports/attendance`) are intentionally *not* admin-gated because non-admin privilege/appointment holders use them — those pages and their APIs do their own scoping instead (see `getManagedGroupIds()` in `guards.ts`). «Informes» only shows in the menu (web and app «Más») with `reports_all`, `reports_group` (group overseers and assistants get it by appointment, `migrations/0085`), `field_service_reports` or `meeting_attendance_recorder`; one's own report and card are reached from Mi Panel.

### Enlaces a JW Library (programa de reuniones)

En el programa (web `/meetings` y app) las partes **numeradas** de entre semana, el estudio de **La Atalaya** y, solo para **ancianos y siervos ministeriales** (`isElderOrMinisterialServant`), el **bosquejo** del discurso público abren JW Library (`https://www.jw.org/finder?…&docid=…&par=…`, el enlace «Compartir» de JW Library: en el teléfono abre la app; `jwlibrary://` no funcionó; `lib/jw/library.ts`, prueba `jwLibrary.test.ts`), no wol.jw.org. La guía guarda en `midweek_meetings` el documento de la semana (`mwb_doc_id`, el nombre del capítulo del EPUB) y el párrafo de cada parte por número (`mwb_pars`, el `data-pid` del encabezado); La Atalaya, `weekend_meetings.watchtower_doc_id` (`migrations/0088`). Los llenan la importación y el job diario. El bosquejo se busca **por número** en `S34_DOC_IDS` (sacado del S-34_S.jwpub, tabla Document; no se puede calcular). Las APIs devuelven `jwLink` por parte, `watchtowerLink` y `talkOutlineLink`. En el programa (`GET /api/weekend/[id]`) el **número** del bosquejo solo llega a ancianos y siervos ministeriales (y a quien administra el fin de semana, que arma el programa); los demás ven solo el título.

**Importar la guía o correr el job diario nunca cambia asignaciones** (`lib/mwb/applyProgram.ts`, `planProgramMerge` puro con pruebas): cada reunión existente se deja igual que la guía (encabezado, canciones, estudio, enlaces y datos de cada parte, emparejadas por tipo y posición), se agregan las partes nuevas y las que ya no están se borran **solo si nadie las tiene asignadas** (si alguien las tiene, se conservan al final). Solo escribe lo que cambió. La Atalaya igual: título, canciones y enlace quedan como la edición publicada, sin tocar a los asignados.

### Bosquejos (S-99a)

Fin de semana → Historial importa el S-99a «Títulos de los discursos públicos ordenados por temas» (no está en las descargas públicas de JW.ORG, se baja del Hub) en **EPUB o PDF** con `lib/publicTalks/parseS99a.ts` (prueba `parseS99a.test.ts`): el EPUB se lee en el servidor (`parseS99aEpub`); el PDF se lee en el navegador con `pdfjs-dist` (`lib/publicTalks/pdfText.ts`, carga diferida; pdf.js no cabe en el Worker) y `parseS99aText` (categorías en MAYÚSCULAS, títulos partidos en dos renglones se unen, el pie «S-99a-S 2/26» se ignora), y se manda la lista ya armada como JSON a la misma ruta, que la valida. Las dos vías terminan en `lib/publicTalks/importOutlines.ts::applyOutlineImport`. **Catálogo central:** el router (`micongre-router`, `GET/PUT /__router/catalog/outlines`, ver su README) guarda la lista oficial; cada instalación la lee con su clave de relay (`PUSH_RELAY_URL`/`PUSH_RELAY_KEY`) en el job diario (paso `outlines`, `lib/publicTalks/catalogSync.ts`) y la aplica igual que una importación. El mismo importador, **sin elegir archivo**, lo trae al momento (`{catalog: true}`). Se publica desde ese importador con «Publicar para todas las congregaciones», que solo ve un admin de la instalación con el secreto `CATALOG_PUBLISH_KEY` (`npm run clave-catalogo` en el router). El bosquejo 0 no existe (lo quitó `migrations/0086`). Los números retirados («(No usar)» en la edición nueva, «(No está disponible)» en la anterior) marcan el bosquejo **«No usar»** (`public_talk_outlines.active = false`): si ya existía conserva su título y solo se marca; si no, se crea con «No usar» como título. Uno que vuelve con título pierde la marca. La marca también se cambia a mano en el editor del bosquejo y se muestra en el Historial, el editor y la lista de oradores y los selectores de bosquejo.

### Canciones (reuniones)

Catálogo `songs` (número = identificador, título) del EPUB «Cantemos con gozo» (sjj): se importa en Fin de semana → Historial (EPUB o «Descargar de JW.ORG») y `lib/songs/catalog.ts::ensureSongsCatalog` lo baja solo, si está vacío, desde el importador de reuniones y el job diario. Entre semana guarda los números en la reunión (`opening/middle/closing_song_number`, que llena el importador de la guía mwb); fin de semana guarda la de La Atalaya y la final en la reunión, y la del discurso público en `speaker_outlines.song_number` (cada orador tiene su canción por bosquejo). Las APIs de reunión devuelven también `...SongTitle`; se muestra «Canción 65: título» en el planificador (cada una en su lugar del programa), el S-140 y Android (`lib/songs/label.ts`).

**Estudio de La Atalaya (fin de semana):** `lib/weekend/watchtower.ts` baja de JW.ORG el EPUB de La Atalaya (ed. estudio, `pub=w`) — la edición de un mes trae los estudios de dos meses después — y completa en `weekend_meetings` el título (`watchtower_title`) y las dos canciones (la del inicio = `watchtower_song_number`, la final = `closing_song_number`) de cada semana, solo donde están vacíos. Lo corren el botón de descargar del planificador de fin de semana (`POST /api/weekend/month`) y el job diario.

**Orden de la reunión de fin de semana:** `weekend_meetings.watchtower_first` (casilla «Iniciar con La Atalaya» (solo quien administra el módulo de fin de semana puede cambiarla; la API ya lo exige)). Normal: canción del discurso (la del orador para ese bosquejo) → discurso → canción de La Atalaya → estudio → canción al terminar La Atalaya + oración. Con La Atalaya primero: canción de La Atalaya → estudio → canción al terminar → discurso → canción del discurso + oración. En el programa y en la app las canciones no se llaman «inicial/final», solo «Canción N: título», cada una junto a su parte.

**Mensaje para oradores (fin de semana):** pestaña «Mensaje» con dos plantillas editables (`weekend_message_templates`: `incoming` = invitado que llega, `outgoing` = local que sale) con palabras clave entre llaves (`lib/weekend/messageTemplate.ts`: `{orador}`, `{congregacion_orador}`, `{congregacion_destino}`, `{dia}`, `{fecha}`, `{hora}`, `{bosquejo_numero}`, `{bosquejo_titulo}`, `{cancion}`, `{direccion}`); una línea cuyas palabras clave queden vacías se omite. `GET /api/weekend/message?kind=incoming&meetingId=…` / `kind=outgoing&outgoingId=…` arma el texto con los datos reales (fecha real de la reunión según el día configurado) y `CopyMessageButton` lo copia al portapapeles: junto al orador invitado en el planificador y en cada discurso enviado.

### Eventos de la congregación (`/events`)

Módulo «Eventos» con el mismo acceso que Congregación (`congregation_access`): Conmemoración, Asamblea de circuito, Asamblea regional, Visita del superintendente y Otro (`congregation_events`, `migrations/0076`, reglas puras en `lib/events/rules.ts` con pruebas, servicio en `lib/events/service.ts`). Un evento afecta la semana (lunes a domingo) de su fecha de inicio y configura cada reunión por separado: sin cambio, **cancelar** (la reunión queda cancelada con `event_id`, pierde todas sus asignaciones —partes, presidente, oraciones, orador, conductor, lector y acomodadores— y planificadores, S-140 y la app muestran el evento en su lugar) o **mover** a otro día y hora de esa semana (`readMeetingSchedules` agrega `overrides` y `effectiveMeetingDate`/`effectiveMeetingTime` los respetan). Borrar o cambiar el evento devuelve la reunión a «programada» (sin las asignaciones que se quitaron). Se avisa a toda la congregación (feed + push) `notify_days_before` días antes (15 por omisión) con el texto opcional **recortado** (`shortText`, 140 caracteres); desde ese día y hasta que termina, el evento sale en **«Próximos eventos»** de Mi Panel (`GET /api/events/upcoming`, `isUpcomingVisible`, `components/panel/UpcomingEvents.tsx`: título y comentario en tono tenue; al tocarlo, un modal con las fechas, qué pasa con cada reunión y el comentario completo); el job diario (paso `events`) aplica los eventos a las reuniones creadas después y manda los avisos pendientes. La visita del SC crea, mueve y borra su propio evento (no se borra desde Eventos), guarda sus 3 discursos con canción (`co_visit_schedules.*_talk_*`) y cambia el programa: entre semana el discurso de servicio reemplaza al estudio y no hay sala auxiliar; fin de semana él da el discurso público, La Atalaya dura 30 min y sigue su discurso final. Las APIs de reunión devuelven `event`, `coVisit`, `date` y `time` (`meetingContext`); `GET /api/congregation/schedule?week=` da el horario de esa semana para la app.

### Tiempo de asignaciones (solo Android)

Privilegio «Ver tiempo de asignaciones» (`meeting_timer`, `migrations/0075`; lo recibe solo el nombramiento `auxiliary_counselor` «Consejero auxiliar», y a otros se otorga a mano). En la pantalla de reuniones de la app, quien preside esa reunión (`chairmanUserId`), el consejero auxiliar o quien tenga el privilegio ve un botón de reloj: cronómetro local (no se guarda en el servidor) con la hora en que debe iniciar cada asignación y cuánto duró cada una. Se cuenta todo: canciones (5 min), oraciones (2 min, aparte: inicial —salvo que la congregación la omita entre semana— y final, en las dos reuniones) y partes, y **siempre 1 min de cambio entre un elemento y el siguiente** (canciones y oraciones incluidas; se espera «Empezar»). Web `lib/meetings/timer.ts` y app `data/MeetingTimer.kt`, iguales. La web no tiene pantalla para esto. El cronómetro tiene **pantalla completa** (debajo de las pestañas: la parte arriba, el tiempo lo más grande que quepa y los mismos botones abajo; se lee aun con la app en una ventanita).

**Reuniones en la web (`/meetings`, para quien no tiene la app: iPhone, Mac):** la misma pantalla que Android (`components/meetings/program/`): pestañas con día y hora, semana, programa en solo lectura con las barras de sección con los íconos y colores de la app (`SectionIcon`, tokens `--meeting-*`), cronómetro (`lib/meetings/timer.ts` con pruebas, guardado en `localStorage`) y botón de asistencia. Los planificadores siguen en `/meetings/midweek` y `/meetings/weekend`.

**Asistencia desde Reuniones (Android):** botón flotante (arriba del reloj) para registrar la asistencia de la reunión que se ve, con los contadores de Informes › Asistencia y lo ya registrado precargado. Lo ven admin, el privilegio de registro de asistencia, el **secretario** y los **acomodadores de entrada y de auditorio asignados a esa reunión** (`canRecordAttendanceFor` en `guards.ts`, que también usa `POST /api/attendance`; `GET /api/attendance?meetingType&meetingId` devuelve `canRecord`).

### Novedades («¿Qué hay de nuevo?»)

Pantalla que sale al entrar (web: `components/announcements/WhatsNew.tsx` en el layout de `(app)`; Android: `WhatsNewPrompt` en `MainShell`) con las novedades **publicadas** que le tocan a la persona y que aún no cerró; al tocar «Entendido» (`POST /api/announcements/[id]/seen`, tabla `announcement_views`, `migrations/0089`) no vuelve a salir en ningún dispositivo. El contenido vive en el código: `lib/announcements/catalog.ts` (`id` permanente, `audience` `all` | `appointed` = ancianos y siervos ministeriales con nombramiento vigente | `admins`, `published`). Contenido: `title`, `image` opcional (archivo en `public/announcements/`, se ve a todo el ancho y **200 px/dp de alto** recortada con *cover*; recomendado 1200 × 600 px con lo importante en el centro, 1000 × 460), `intro`, `body` en Markdown sencillo (el de los avisos: negrita, cursiva, títulos, listas, enlaces; web `NotificationMarkdown`, app `ui/SimpleMarkdown.kt`) e `items` opcionales. Imagen, título y texto van en un solo contenedor con scroll; «Entendido» queda fijo abajo. La app baja la imagen con su sesión (`siteFile`). Si hay varias para la persona, salen una tras otra. Se escriben con `published: false` y **solo se publican cuando el usuario lo pide** (cambiar a `true` y desplegar). Reglas puras en `rules.ts` con pruebas; `GET /api/announcements` las filtra por nivel (los tres niveles, web y app).

### Vista mensual de los planificadores (pantalla completa)

Botón «Vista mensual» (`MonthPlannerButton`, `components/planner/MonthPlanner.tsx`) en el encabezado de Entre semana, Fin de semana y Acomodadores; la vista semanal sigue siendo la de siempre. Abre a pantalla completa una tabla del mes (cada semana en el mes de su lunes): a la izquierda las asignaciones (las partes de la reunión o la plantilla de acomodadores) y arriba una columna por reunión con su fecha real (acomodadores: entre semana y fin de semana juntas). `GET /api/planner/month?module=midweek|weekend|operational&date=` (`lib/planner/month.ts`, ~10 consultas; las filas de cada reunión se juntan con `mergeRowOrder` de `lib/planner/rows.ts`, puro con pruebas; nombres repetidos se numeran) devuelve columnas, filas, casillas (`target` = a dónde se guarda), elegibles por privilegio y nombres. Se guarda todo junto con los endpoints de siempre (que revalidan), en paralelo (`mapWithLimit`, hasta 6), una petición por reunión, parte o asignación; lo que falla queda marcado en rojo. El discursante de fin de semana solo se muestra (se arregla en su pantalla). Al cerrar, la semana se vuelve a leer.

### Asignación automática (`lib/assignments/`)

Botón «Asignar automáticamente» (`components/assignments/AutoAssignButton.tsx`) en entre semana, fin de semana y tareas operativas: `POST /api/assignments/suggest` (solo lectura, guardas por módulo) devuelve, para cada casilla **vacía**, la persona propuesta y los candidatos con sus números de los **3 meses anteriores a esa reunión** (hasta el día antes de su fecha real, así lo ya asignado en semanas futuras también cuenta); el diálogo es una vista previa editable y «Aplicar» solo llena el borrador de la pantalla (se guarda con «Guardar», que revalida la elegibilidad como siempre). Se desactiva si hay cambios sin guardar (la propuesta usa lo guardado). **No hay tablas ni migraciones: todo al vuelo**, ~13-15 consultas D1 por pulsación (límite de la capa gratuita: ~50 por invocación), así que cualquier ampliación debe seguir cargando por rango de fechas con joins y sin una consulta por persona o privilegio.
- `stats.ts::loadAssignmentStats`: cuenta por usuario y tipo (`midweek:*`, `weekend:*`, `operational:<privilegeId>`) con la fecha real (`effectiveMeetingDate`), sin reuniones canceladas ni fechas futuras. Los oradores, discursos salientes, limpieza, territorios y predicación todavía no cuentan ni se asignan.
- `suggest.ts::proposeAssignments`: motor puro y determinista. Disponible = elegible + sin otra asignación en la reunión + no repetido en la corrida (quien está ocupado solo en otro módulo es último recurso, marcado). Orden: menos veces con esa asignación, menor carga total, última vez más antigua, nombre. Partes de estudiante respetan `getStudentPartRule` y la pareja del ayudante (`isValidAssistantPairing`). El conductor de La Atalaya no se rota: va el del nombramiento `watchtower_conductor` si hay uno elegible.
- `rbac/eligibility.ts`: `applyPrivilegeConstraints` (núcleo puro compartido), `getEligiblePublishers` (por privilegio) y `loadEligibilityContext` + `eligibleFromContext` (todos los privilegios con 5 consultas). Cualquier regla de elegibilidad nueva va en el núcleo para que ambos caminos coincidan.
- `plan.ts` arma las casillas de cada reunión (`chairman`, `openingPrayer`, `a:<id>:main|assistant`, `o:<slotId>`…); esas claves son las que cada pantalla vuelca a su borrador.

### Escrituras sin internet de la app Android (idempotencia)

La app guarda en una cola local (con el teléfono sin señal) el informe de servicio (`POST /api/reports/s4`), la asistencia (`POST /api/attendance`), completar/devolver un territorio (`POST /api/territories/assignments/[id]/resolve`) y ocultar un aviso (`POST /api/notifications/[id]/dismiss`), y los reintenta al volver internet. Para que un reintento nunca repita el efecto, cada operación lleva la cabecera `Idempotency-Key` (`lib/http/idempotency.ts`, tabla `processed_operations`, que el job diario limpia a los 45 días): si ya se procesó, la ruta responde `{ok:true, duplicate:true}`; la clave solo se registra cuando la operación salió bien (un 409 no la consume). Informe y asistencia aceptan además `baseVersion` (segundos de `submittedAt`/`recordedAt` sobre los que se editó; `null` = no había registro): si el servidor tiene otra versión responde **409 `conflict`** con el registro actual y NO pisa nada (la app conserva el cambio y avisa). Sin `baseVersion` el comportamiento es el de siempre. Las respuestas de informe y asistencia devuelven `version`.

**Oradores en el planificador de fin de semana:** `GET /api/weekend/speakers?forAssignment=true&meetingId=…` ofrece los locales (elegibles) y, de los visitantes, solo los de las congregaciones con un arreglo de discursos (`talk_arrangements` en estado `planned`, `pending` o `accepted`) en el mes al que pertenece el **primer día (lunes) de la semana** de esa reunión (no el del sábado); el orador ya asignado siempre se conserva y, **si ese mes no hay ningún arreglo, se ofrecen todos**. Los locales salen **todos** (incluso los marcados como inactivos: esa marca es solo para los discursos que salen, que usan `kind=local` sin `meetingId` y solo ofrecen locales activos). En la pestaña Oradores cada orador es una fila retráctil (contraída: nombre, «Activo»/«Inactivo» y su congregación o «Local»; al tocarla, sus bosquejos con número y canción) con los botones Llamar, WhatsApp, Activar/Desactivar (sin abrir el editor) y Editar; el buscador encuentra por nombre o congregación; el editor lista primero los bosquejos que ya tenía y luego los demás, por número. Hay filtro por estado y el reporte `local-speakers` «Oradores públicos aprobados para [Mes] [año]» (botón en el encabezado de la pestaña; ancianos y luego siervos ministeriales, por nombre, con sus datos en una línea —solo los que tiene— y una tabla de bosquejos: número, título, canción) (`?status=active|all`, `lib/export/builders/localSpeakers.ts`) descarga los locales activos o todos. El reporte del planificador **«Invitados (mes)»** (`incoming-talks`, `lib/export/builders/incoming.ts`) lista los oradores visitantes del mes (cada semana en el mes de su lunes) con su congregación y la fecha real de cada discurso; el título lleva las congregaciones con arreglo ese mes y el subtítulo el día y la hora de la reunión de fin de semana de Congregación.

### Informes → pestaña «Grupos»

Pestañas de Informes: **Tarjetas** (`/reports`, lista por persona), **Grupos** (`/reports/groups`) y **Asistencia** (solo con el privilegio de registro de asistencia). «Grupos» muestra, para el mes elegido (por defecto el actual), una tabla por grupo de servicio en orden alfabético (los sin grupo, al final) con las columnas de la S-21: participó, cursos, auxiliar, horas (+ proyectos) y notas, más totales. `GET /api/reports/groups?year=&month=` usa el mismo alcance que la tabla S-4 (`getReportsGroupIds`): quien solo ve un grupo, solo recibe ese; sin grupos → 403. Reporte descargable (Excel, Word o imagen) con el botón de la pestaña: builder `lib/export/builders/informesGrupos.ts` (`reports-groups`, una tabla por grupo con totales, mismo alcance). Android: `GroupReportsScreen` dentro de `ReportsHost` (visible con `canSeeGroupReports`).





### Notificaciones push en la web (iPhone, iPad, Mac, computadoras)

Web Push con VAPID (`lib/push/dispatch.ts`, `public/sw.js`, suscripción en `lib/push/client.ts`). La web es instalable (`src/app/manifest.ts` → `/manifest.webmanifest`, íconos en `public/icons/`, `appleWebApp` en el layout; el middleware deja pasar el manifiesto y los íconos): en iPhone/iPad (iOS 16.4+) Safari solo entrega avisos a Mi Congre abierta desde la pantalla de inicio. `pushAvailability()` dice `ready`, `install` (iPhone sin instalar: se muestran los pasos Compartir → Agregar a inicio, `IosInstallSteps`) o `unsupported`. Mi Panel muestra `PushPrompt` (activar avisos o los pasos de iPhone; se oculta si ya están activos, si el navegador los bloqueó o si la persona lo cierra, `localStorage`) y Mi perfil el interruptor `PushToggle`.
