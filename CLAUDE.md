# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install                    # install dependencies
npm run dev                    # Next.js dev server (localhost:3000)
npm run typecheck              # tsc --noEmit
npm run build                  # next build (production build, no Cloudflare bundling)
npm run check                  # typecheck + build, run this before considering a change done
npm run preview                # opennextjs-cloudflare build + wrangler dev (emulates the real Worker + D1 locally)
npm run deploy                 # opennextjs-cloudflare build + opennextjs-cloudflare deploy (publishes to Cloudflare)
npm run db:migrate:local       # apply migrations/*.sql to local D1 (.wrangler/state)
npm run db:migrate:remote      # apply migrations/*.sql to the production D1 database
npm run db:create-admin        # node scripts/create-admin.mjs "Full Name" username password [--remote]
npm run cf-typegen             # regenerate worker-configuration.d.ts from wrangler.json bindings
```

There is no test suite and no lint script configured. `npm run check` is the closest thing to a full verification pass; run it after any change, and manually smoke-test through the browser (login → the module you touched) since there's no automated coverage.

Local dev needs a `.dev.vars` file (copy `.dev.vars.example`) with a `JWT_SECRET`. `next dev` picks it up via `initOpenNextCloudflareForDev()` in `next.config.mjs`, which lets `getCloudflareContext()` work outside of `wrangler dev` too.

Bootstrapping: while no user has `system_role='admin'`, `src/middleware.ts` redirects *every* route (pages → `/setup`, APIs → 409 `setup_required`) to the **setup wizard** (`src/components/setup/SetupWizard.tsx`); once an admin exists everything behaves normally and `/setup` redirects to `/`. The middleware caches "setup complete" per isolate, so after hand-wiping users in a dev DB restart the server. Wizard steps, each persisted immediately through public `/api/setup/*` routes (`src/lib/setup/service.ts`; all reject with 409 once an admin exists): welcome → source (Hourglass upload via a modal with progress + summary, or start empty) → congregation data (preloaded from the DB, i.e. from the migration), with an optional "Traer los datos desde JW.ORG" box (`JwCongregationLookup` → public `POST /api/setup/jw`, reusing `src/lib/jw/hub.ts`) that fills name, address and meeting times from a hub.jw.org link → super-admin account (name, username, password; created *last* and as a *hidden* admin so it doesn't count as a publisher; then the UI fades out and goes to `/panel`). A failed Hourglass import is rolled back, and it refuses to run over existing users. The mapping in `src/lib/setup/hourglass.ts` mirrors `scripts/import-hourglass.mjs` (keep them aligned). **NWScheduler** source (`src/lib/setup/nws.ts`, `NwsImportModal`, `POST /api/setup/nws`): NWS exports one CSV per option, so the modal asks for up to five (Personas required; Contactos de emergencia, Informes, Discursantes, Programa de discursos públicos optional). Files are recognised by their header columns, never by file name; the same pure `buildNwsImport` runs in the browser for a dry-run preview and on the server for the real (all-or-nothing, rolled back with `wipeAllData`) import. Reports/speakers/program rows are joined to people by normalised name (repeated names are skipped with a warning). Referenced talk outlines missing from the catalog are created as `Discurso N` placeholders. Third source: **restore a MiCongre backup** (`POST /api/setup/restore`). Backups (`src/lib/backup/backup.ts`) are generic JSON dumps of every table (discovered from `sqlite_master`; catalogs `privileges`/`appointment_privilege_rules` and session/activation tokens excluded); restore validates table/column names against the live schema and runs in one D1 batch with `defer_foreign_keys`. Admin-only **Congregación → Zona de peligro → Borrar todos los datos** (`DeleteAllDataCard`) downloads that backup via `GET /api/congregation/backup`, then `POST /api/congregation/reset` wipes everything except catalogs, which puts the app back in setup mode (the middleware caches "setup complete" for only 30 s for this reason). `db:create-admin` is still the CLI alternative.

## Architecture

Congregation-management web app (Jehovah's Witnesses congregation administration — publishers, appointments/privileges, meeting scheduling, operational tasks, service reports, attendance). Next.js App Router, deployed to Cloudflare Workers via OpenNext, with Cloudflare D1 (SQLite) via Drizzle ORM. Phase 1 of 2 — a future Android app (not in this repo) will consume the same `/api/auth/*` and other API routes, which is why auth is token-based rather than pure server-session.

### Migrations are hand-written, not drizzle-kit-generated

`migrations/*.sql` is applied via `wrangler d1 migrations apply` (the numbering convention from the original Cloudflare D1 template). `drizzle.config.ts` exists only to power `drizzle-kit studio`; **do not run `drizzle-kit generate`** — it would produce a second, disconnected migration history. When the schema in `src/db/schema/*.ts` changes, hand-write the matching SQL in a new `migrations/NNNN_*.sql` file with the same column names/types/constraints, and apply it locally and (when ready) remotely. `migrations/0009_field_service_groups.sql` is the pattern to follow when a column's FK target doesn't exist yet at table-creation time (add the column later via `ALTER TABLE`).

### Auth: dual web/mobile from day one

`src/lib/auth/*` implements auth from scratch (no Auth.js) with only Web Crypto (`crypto.subtle`), so it runs identically in Workers and in `next dev`:
- Passwords: PBKDF2-SHA256 (`password.ts`), never bcrypt/argon2 (those need node-native bindings Workers doesn't have).
- Access tokens: hand-rolled HS256 JWT (`jwt.ts`), 15 min TTL, carries `privs` (privilege codes) so most requests don't need a DB round-trip to check authorization.
- Refresh tokens: opaque, hashed at rest (`refresh_tokens` table), rotated on every use; **reusing an already-rotated token revokes the entire session family** (`api/auth/refresh/route.ts`) — this is the theft-detection path.
- Every `/api/auth/*` route sets httpOnly cookies **and** returns the tokens in the JSON body in the same response — the web client uses the cookies, a future mobile client uses the JSON. `src/middleware.ts` and `src/lib/auth/session.ts` both resolve identity the same way: cookie first, `Authorization: Bearer` header as fallback.
- There is no email/password-reset-by-email flow. Login is by `username` (system-generated, see below), because email addresses are unreliable for this user base. The only account-provisioning path is the **activation link**: an admin generates a one-time link from a publisher's detail page (`AccessPanel.tsx` → `POST /api/publishers/[id]/access`), the recipient opens it (`/activar/[token]`), and `POST /api/auth/activate` generates a username + password for them and logs them in immediately — nobody ever invents their own password. See `docs/mobile-activation-protocol.md` for the exact contract the future Android app must implement against the same endpoint (it's designed to work as an Android App Link against the identical URL).
- **Eliminar cuenta** (requisito de Google Play): `POST /api/auth/delete-account` (`{password}`, desde Mi perfil web o la app) llama a `lib/auth/deleteAccount.ts::removeAccountAccess`: borra usuario, contraseña, sesiones, tokens de dispositivo, suscripciones push y enlaces de activación y deja `account_status='no_account'`, **pero no borra al publicador** (ficha, nombramientos, informes: son registros de la congregación; quien los quiera borrar se lo pide a un admin). Un admin que sea el último con acceso recibe 409 `last_admin`. Las URL públicas que pide Play (privacidad, eliminar cuenta) y el `assetlinks.json` del dominio comodín los sirve `micongre-router`; este repo también sirve `/.well-known/assetlinks.json` (`lib/android/assetlinks.ts`, mantenerlo igual que el del router) para los sitios en `workers.dev`.

### RBAC: one eligibility engine, reused everywhere

`src/lib/rbac/eligibility.ts::getEligiblePublishers(db, privilegeId)` is the single source of truth for "who is allowed to do X". It unions two paths — automatic eligibility via an active `theocratic_appointments` row matched against `appointment_privilege_rules`, and direct grants in `user_privileges` — then filters by the privilege's hard constraints (`requires_male`, `requires_baptized`, `requires_adult`/parental-consent). Every "assign a person" UI (meeting planners, operational matrix, weekend roles) calls the **same function** to populate its dropdown and the API re-calls it via `assertEligibleForAssignment()` before persisting, so a stale or tampered client can never force an invalid assignment. `PRIVILEGE_IDS` in `src/lib/rbac/roles.ts` hardcodes the literal `id` values seeded in `migrations/0005_privileges_rbac.sql` — server and client code reference privileges by these constants rather than looking up `code → id` at runtime.

`GET /api/privileges/eligible?privilegeIds=a,b,c` batches multiple privilege lookups into one request — meeting-planner and operational-matrix pages fetch the full set of privilege IDs they might need once on load, rather than one request per dropdown.

Other guards in `src/lib/rbac/guards.ts`:
- `assertCanManageReport(db, session, targetUserId)` — the dual-authorship rule for S-4 reports: a publisher manages their own, **or** the superintendent/assistant of their `field_service_group` (verified by both the group's `overseerUserId`/`assistantUserId` *and* an active `field_service_group_overseer`/`assistant` appointment), **or** any admin (admins bypass the group check entirely).
- `assertCanRecordAttendance(session)` — admin or the `meeting_attendance_recorder` privilege; this is why `/api/midweek` and `/api/weekend` GET (list only, not the `[id]` detail) are open to any authenticated user rather than admin-only — a non-admin attendance recorder needs to see meeting dates to pick which one to record.
- `isValidAssistantPairing()` in `eligibility.ts` — same-sex-or-same-`householdId` rule for a student assignment's assistant.

### Schema quirks worth knowing before touching them

- `operational_schedules` and `meeting_attendance` are **polymorphic**: `meetingType` (`midweek`|`weekend`) + `meetingId`, no real FK, because SQLite/D1 can't FK to one of two tables. Integrity is enforced in application code (`src/lib/collision.ts` resolves the right table per `meetingType`).
- `midweek_assignments` has generic `mainAssigneeId`/`assistantAssigneeId` columns reused across very different section types. The "Estudio bíblico de la congregación" section is modeled as **two separate rows** (conductor + reader, each with its own `privilegeId`, distinguished by `sectionTitle`) rather than adding more columns — see `MIDWEEK_FIXED_SECTIONS` in `roles.ts`. `student_assignment` is the only section type that isn't auto-seeded when a meeting is created (its count varies week to week); everything else is seeded once via `MIDWEEK_FIXED_SECTIONS`.
- `service_reports.userId` (whose report it is) is deliberately separate from `enteredByUserId` (who actually typed it in) — needed for the dual-authorship feature above without a full audit-log table.
- `users.account_status` (`no_account`/`invited`/`active`/`disabled`) is independent of `congregationStatus` (active/inactive/irregular) and of having appointments/privileges — a student or a child can exist fully in the system with no login ever provisioned.
- Collision detection (`src/lib/collision.ts`) is advisory only (returned as `warnings[]` on the assignment response), never blocking — an admin can still save an assignment that double-books someone.

### Limpieza del Salón del Reino (`/cleaning`)

Módulo gateado por el privilegio `cleaning_admin` ("Administrar limpieza", otorgado a mano; admin siempre puede), con la terminología de la Guía y el Cronograma oficiales (`src/lib/cleaning/labels.ts`, incluye un resumen de las guías). Tres tipos (`cleaning_tasks.kind`): **ligera** (después de cada reunión; una tarea por reunión, `meeting_type` + `meeting_id` polimórfico sin FK real, igual que `operational_schedules`), **profunda** (cada semana; `week_start` = lunes) y **a fondo** (por lo menos una vez al año; `task_date`, se programa a mano y puede haber varias). Los responsables (`cleaning_task_assignees`, varios por tarea) son un **grupo de servicio nuestro**, **toda nuestra congregación**, u **otra congregación del salón** (catálogo `cleaning_congregations`, pestaña "Congregaciones del salón"): lo que queda a cargo solo de otra congregación no genera avisos en la nuestra. Las tareas ligera/profunda se crean al asignar o marcar por primera vez y se borran solas al quedar sin responsables ni marca (`lib/cleaning/tasks.ts`); valida el responsable **antes** de crear la tarea.

Asignar (`POST /api/cleaning/assignees`) no avisa: el botón **Enviar notificación** de cada fila (`POST /api/cleaning/tasks/[id]/notify`) crea una `notifications` por responsable nuestro (scope `group` con el `groupId` asignado, o `congregation` si es toda la congregación; `expiresAt` = fin de la limpieza; cada integrante puede ocultarla) más el push, y reenviar o quitar al responsable borra el aviso anterior. El recuadro "Realizada" (`POST /api/cleaning/complete`) es el que marca el coordinador de limpieza en el cronograma. La asignación aparece en "próximas asignaciones"/"historial" de Mi Panel (`getUserAssignments`, con `dateEnd` para la semana de la profunda) con o sin aviso; reuniones canceladas o borradas se omiten. **Generar cronograma** (`/cleaning/schedule`, `lib/cleaning/schedule.ts`) dibuja el formulario oficial del año (ligera ES/FS por semana 1–5 × mes, profunda, a fondo), con o sin lo asignado, para imprimir/guardar como PDF; cada semana cae en el mes de su lunes. D1 limita a 100 parámetros por consulta: los `inArray` que pueden crecer usan `chunked()`.

### Territorios (`/territories`)

Acceso: admin o el privilegio `territory_management` ("Siervo de territorios"), que reciben solos el superintendente de servicio y el siervo de territorios (reglas en `migrations/0046`). Dos tipos (`territories.kind`): **general** (mapa con polígonos, líneas, puntos y textos) y **public_preaching** (solo puntos y textos; la API rechaza otra cosa con `map_not_allowed`, ver `hasDisallowedFeatures`). El dibujo es un GeoJSON FeatureCollection en `territories.map_data` (los textos son `Point` con `properties.kind="text"`; los puntos pueden llevar `properties.emoji`). Mapa base gratuito: teselas vectoriales de OpenFreeMap con MapLibre GL, estilo "bright" sin nombres de lugares (`lib/territories/mapStyle.ts`); `lib/territories/mapController.ts` es el editor (solo cliente; puntos y textos son marcadores HTML para que se vean los emojis) y `importFile.ts` importa KML/KMZ/GeoJSON. Se puede encargar un territorio solo a quien tenga el privilegio otorgado a mano "Asignable para territorio" (tipo General) o "Asignable para predicación pública" (`migrations/0047`; `listAssignableUsers`, que `assignTerritory` revalida). El módulo tiene dos pestañas: **Asignaciones** (listado con acciones de administrador: avisar, completar, devolver, cancelar, eliminar) y **Territorios** (una tarjeta por territorio). Cada asignación (`territory_assignments`) queda de historial; a lo más una vigente por territorio. Asignar no avisa: el botón **Enviar** (`POST /api/territories/[id]/notify`) crea la notificación + push. En Mi Panel el territorio sale como asignación hasta que el encargado lo **completa** o **devuelve** (comentario opcional, con confirmación; `POST /api/territories/assignments/[id]/resolve`, solo el propio encargado), y eso avisa (notificación + push) a quienes tienen el privilegio. Los `title` de `Button` y `components/ui/Tooltip` son el globito de ayuda estándar de la app.

### Route/module dependency order

If extending the app, this is the order things were actually built in and the order their data dependencies require: schema/migrations → auth → RBAC eligibility engine → publishers (+ appointments/privileges grants, which live under `api/publishers/[id]/...`) → field service groups → the two meeting planners (midweek, weekend — independent of each other, both depend on eligibility) → operational tasks matrix (depends on both meeting planners existing, for collision checks) → reports/attendance (depends on field service groups for dual authorship) → the regular-user panel (`/panel`, reads across all of the above via `src/lib/queries/panel.ts`, built last since it has no writes of its own besides self-service S-4).

Admin-gated pages redirect to `/panel` server-side (`if (session?.role !== "admin") redirect("/panel")`); a few pages (`/reports`, `/reports/attendance`) are intentionally *not* admin-gated because non-admin privilege/appointment holders use them — those pages and their APIs do their own scoping instead (see `getManagedGroupIds()` in `guards.ts`).
